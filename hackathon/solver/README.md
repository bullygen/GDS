# Планировщик группировки Cosmo B

Построитель принимает сценарии из `hackathon/data`, создаёт сетку действий
GDS, генерирует корректную популяцию и оптимизирует её методом GDE3.
Энергия, температура, нагреватель, калибровка, окна, непрерывность заданий
и общий лимит downlink проверяются в C++ внутри построителя.
Python отвечает за ввод, эволюционный отбор, исполнение через исходный
интерпретатор, версии расписания и отчёты.

## Запуск локально на Linux

Команды выполняются из корня репозитория. Нужны Python 3.10+, компилятор
C++17 и CMake 3.18+. В Ubuntu системные зависимости можно установить командой
`sudo apt install python3-venv python3-dev build-essential cmake`.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r hackathon/solver/requirements.txt
.venv/bin/python hackathon/solver/run.py build

.venv/bin/python hackathon/solver/run.py solve \
  --scenario hackathon/data/P01_intro.json \
  --objective pareto --population 8 --generations 5 --attempts 8 \
  --output hackathon/solver/outputs/intro_run
```

Сборка расширения использует `src/network.cpp` и `include/gds/network.hpp`
из этого репозитория. Устанавливать основной Python-пакет `gds` для данного
планировщика необязательно. После изменения C++ повторите команду `build`.
Готовое расширение лежит рядом с `native.cpp`, промежуточная сборка — в
`hackathon/solver/build`. Сборки и результаты исключены из Git.

Каталог `--output` должен быть новым или пустым. Повторный эксперимент
сохраняйте под другим именем: предыдущий результат служит воспроизводимым
источником для ветвления.

## Цели и параметры

```bash
# Максимальное найденное число завершённых заданий приоритета 3.
.venv/bin/python hackathon/solver/run.py solve \
  --scenario hackathon/data/P02_shift.json --objective critical \
  --output hackathon/solver/outputs/critical_run

# Максимальная найденная выручка.
.venv/bin/python hackathon/solver/run.py solve \
  --scenario hackathon/data/P02_shift.json --objective revenue \
  --output hackathon/solver/outputs/revenue_run

# Фронт Парето; исполняем его край с максимальной выручкой.
.venv/bin/python hackathon/solver/run.py solve \
  --scenario hackathon/data/P04_demand.json --objective pareto --select revenue \
  --population 12 --generations 10 --seed 42 \
  --output hackathon/solver/outputs/demand_pareto
```

`--generations 0` создаёт только начальное поколение корректных GDS-планов.
`--population` не меньше 4; `--attempts` задаёт число проб разных размещений
каждой заявки. `--differential-weight` — F в `(0, 2]`, `--crossover` — CR
в `[0, 1]`. Зерно и все параметры записываются в метаданные. Бюджет поиска
можно увеличивать, но глобальный оптимум и полный математический фронт
этот эвристический алгоритм не доказывает.

Для Парето сохраняются обе координаты: выручка и доля выполненных известных
заданий приоритета 3. В пределах одной версии знаменатель постоянен,
поэтому отбор по числу таких завершённых заданий эквивалентен отбору по доле.
Если заявок приоритета 3 нет, доля равна JSON `null`. В режиме `critical`
выручка используется только для выбора между равноценными результатами;
в режиме `revenue` аналогично используется число приоритетных заданий.
В режиме `pareto` параметр `--select critical|revenue` явно определяет,
какую точку найденного фронта исполнять. Остальные точки сохраняются.

## События, остановка и ветвление

```bash
.venv/bin/python hackathon/solver/run.py solve \
  --scenario hackathon/data/P02_shift.json \
  --events hackathon/examples/events_demo.json \
  --objective pareto --switch 180:revenue \
  --output hackathon/solver/outputs/events_run

# Остановить исполнение на границе 74; будущие команды не попадут в result.json.
.venv/bin/python hackathon/solver/run.py solve \
  --scenario hackathon/data/P02_shift.json \
  --events hackathon/examples/events_demo.json --until-step 74 \
  --output hackathon/solver/outputs/partial_run

# Другая цель от уже выполненной границы. Родительский файл не изменяется.
.venv/bin/python hackathon/solver/run.py solve \
  --resume hackathon/solver/outputs/partial_run/result.json \
  --branch-step 74 --objective revenue \
  --events hackathon/examples/events_demo.json \
  --output hackathon/solver/outputs/branch_run
```

Три типа сообщений (`add_jobs`, `satellite_outage`, `close_downlink`)
применяются исходным `Session.apply_event` только на своей границе `at_step`.
Будущие сообщения хранятся в драйвере воспроизведения и не передаются
построителю. Порядок событий из файла сохраняется, включая несколько
сообщений на одном шаге. Их изменения входят в одну новую версию.
Переключение цели также создаёт версию. Сообщения на границе остановки
считаются полученными; сообщения после неё отсутствуют в результате.

При перепланировании сохраняются команды и реальные состояния до границы.
Новый экземпляр сети получает только известные на ней данные; физика заново
считается на всём изменяемом суффиксе. Каждый вариант фронта независимо
проверяется исходным интерпретатором до начала исполнения.

Начатый непрерывный блок продолжается на том же аппарате. Если событие
делает его полное продолжение невозможным, выполненные шаги остаются в
истории, а оставшаяся часть не переносится на другое время или аппарат.
Такая заявка учитывается как незавершённая после дедлайна; затраченная работа
входит в `work_steps_in_missed_jobs`. Список есть в `abandoned_jobs` версии.
Это позволяет соблюсти требование непрерывности и не переписывать прошлое.

## Построитель и физика

В [native.cpp](native.cpp) основное состояние — действие каждого аппарата
в каждом слоте. Проекция `y[3*s+a,t]` имеет три строки действий; idle
представлен тремя нулями. Дополнительные селекторы размещения задают целые
блоки одной заявки на одном аппарате. Их области учитывают принадлежность
аппарата, окна, контакты, известные отказы и полное завершение к дедлайну.
Заявка может быть пропущена — это допустимое расписание с меньшей полезностью.

Используется специализированное **блочное стохастическое обновление GDS**:
геном задаёт порядок предложений, начальные размещения и включение заявок;
охрана проверяет каждое предложенное изменение сетки и принимает его при
`U=0`. Добавление всего рабочего блока и при необходимости калибровки
является атомарным обновлением. Данные о стоимости и приоритете в C++-сеть
не передаются. Функционал U складывает штрафы бинарных, общих ресурсных,
энергетических, тепловых, калибровочных и целевых ограничений и непрерывности.
Непересечение блоков на одном аппарате обеспечивается структурно.

Это расширение основной сети для нелинейной модели с памятью. Обычный
`GDSNetwork.run()` над фиксированной квадратичной матрицей сам по себе
не проверяет такую физику. Поэтому файл `grid.gdsw` не является самостоятельным
решателем хакатона: для точного продолжения используйте `prefix.json` и
построитель `Network`. При `downlink_parallel_limit > 1` ограничение общего
канала является кардинальным фактором, его нельзя заменить запретом каждой
пары передач. Разреженная запись в `network.npz` и порог в `network.json`
сохраняют исходное ограничение.

После каждого предложения пересчитываются энергия, температура и возраст
калибровки всех аппаратов на всех шагах изменяемого горизонта. Выполненный
префикс уже зафиксирован и задаёт точные начальные состояния суффикса.
Внутренний цикл не вызывает Python. Между Python и C++ передаётся целый геном
или готовый план, а не отдельные операции физики. Для пакетной установки
статических смещений основной GDS-библиотеки добавлен `set_unary_biases`.

GDE3 в [engine.py](engine.py) использует DE/rand/1/bin, обязательную координату
скрещивания, ограничение генов диапазоном `[0,1]`, попарный отбор, сортировку
фронтов и crowding distance. Начальное поколение содержит случайные геномы
и три внешних посева: приоритет, выручка на рабочий шаг, близость дедлайна.
Каждый геном декодируется сетью в корректное расписание до оценки критериев.
Архив сохраняет недоминируемые пары критериев всех оценённых кандидатов;
при одинаковых координатах достаточно одного представителя расписания.

## Правила исходной модели

В ранних пунктах `HACKATON.md` строгие знаки для границ и критический заряд
расходятся с §9 и исполняемым интерпретатором. Реализация следует
[resource_env.py](../model/resource_env.py) и [operations.py](../model/operations.py):

- начало разрешено при `release_step <= k`, конец — при `k+work_steps <= deadline_step`;
- калибровка и задания требуют заряда **до и после** операции не ниже резерва
  с допуском `1e-9` Вт·ч; критический порог служит отчётности;
- полезная операция допустима, если начальная и расчётная конечная температуры
  включительно находятся в диапазоне; нагреватель и допуск зарядки проверяются
  по начальной температуре;
- задание требует `calibration_age_steps < calibration_valid_steps`;
- idle исполняется и при отказе; энергия ограничивается диапазоном `[0,C]`,
  отрицательная сырая энергия учитывается как brownout;
- снижение заряда idle ниже резерва не делает команду недопустимой.
  Например, даже полностью пустое расписание `P03_energy` имеет три такие
  пары «аппарат—шаг». Они сохраняются в отчёте.

Дополнительное требование непрерывности из задания строже возможностей
исходного интерпретатора и проверяется отдельно. Невыполненные заявки остаются
в учёте; стоимость сохраняется из первоначального сценария/полученного события.
Счётчик `critical_jobs_completed_on_time` в пошаговом отчёте относится к
приоритетным заявкам с уже наступившим сроком. Прогноз оптимизатора относится
к концу горизонта, когда сроки всех известных заявок наступили.

## Проверка и измерение производительности

```bash
.venv/bin/python -m pytest hackathon/solver/test_solver.py -q
.venv/bin/python hackathon/solver/run.py verify \
  --result hackathon/solver/outputs/intro_run/result.json

# Непосредственно исходный интерпретатор, без кода планировщика.
.venv/bin/python hackathon/model/operations.py \
  --result hackathon/solver/outputs/intro_run/result.json \
  --output hackathon/solver/outputs/reference_replay.json

# Все четыре сценария, три цели, все типы событий и отдельная ветвь.
.venv/bin/python hackathon/solver/acceptance.py \
  --output hackathon/solver/outputs/acceptance_run

.venv/bin/python hackathon/solver/benchmark.py \
  --scenario hackathon/data/P01_intro.json hackathon/data/P02_shift.json \
             hackathon/data/P03_energy.json hackathon/data/P04_demand.json \
  --output hackathon/solver/outputs/benchmark_run.json
```

Проверки сравнивают C++ с оригинальной моделью по каждому состоянию каждого
аппарата, срокам завершения и выручке; проверяют неизменяемость прошлого,
отсутствие предвидения событий, непрерывность и нулевые знаменатели.
Полная приёмка дополнительно повторяет все пошаговые сводки и проверяет
наличие рисунков для всех аппаратов. Её параметры по умолчанию — 4 члена,
2 поколения и 8 проб размещения: это воспроизводимая проверка работы,
а не исчерпывающий поиск оптимума.

`benchmark.py` отдельно измеряет компиляцию постановки, декодирование GDS,
полный пересчёт в C++ и исполнение оригинальной Python-моделью. В последнем
случае также создаются словари трассы и проверяются входы; отношение времени
этих операций не следует называть ускорением одной формулы температуры.
Результаты конкретного запуска и покрытие требований описываются в
[VALIDATION.md](VALIDATION.md).

## Использование из Python

```python
from hackathon.model.resource_env import load
from hackathon.solver.engine import Options
from hackathon.solver.project import ScheduleProject

project = ScheduleProject(
    load("hackathon/data/P01_intro.json"),
    objective="pareto",
    options=Options(population=8, generations=5, seed=42),
    preference="critical",
)
result = project.run("hackathon/solver/outputs/python_run")
print(result["summary"])
```
